## Application Overview

- **URL**: https://booking.kai.id
- **Type**: Transportation ticketing — train schedule search, booking, seat selection, payment
- **Owner**: PT Kereta Api Indonesia (Persero)
- **Stack**: Server-rendered pages (jQuery-based), XPath-heavy UI, datepicker/flexdatalist components
- **Users**: Millions of Indonesian commuters daily (peak: Lebaran, holiday seasons)
- **Business Context**: KAI Online Booking is a web-based platform for customers to search train schedules, book tickets, select seats, and complete payments online. Every failed transaction = lost revenue + customer churn to Traveloka/Tiket.com.

## System Architecture (Inferred)

```
┌─────────────┐     ┌──────────────┐     ┌─────────────────┐
│   Browser   │────▶│  Web Server  │────▶│  Booking Engine  │
│  (jQuery)   │◀────│  (SSR HTML)  │◀────│  (Seat Inventory)│
└─────────────┘     └──────────────┘     └─────────────────┘
                           │                       │
                    ┌──────▼──────┐         ┌──────▼──────┐
                    │   Session   │         │   Payment   │
                    │  Management │         │   Gateway   │
                    └─────────────┘         └─────────────┘
```

**Key architectural risks:**
- jQuery + server-rendered → page reloads between steps (not SPA)
- Session-based state → timeout mid-booking = lost cart
- Real-time seat inventory → race conditions (seat taken by others during booking)
- Payment gateway redirect → external dependency (BCA, Mandiri, GoPay, dll)

## Booking Flow (Critical Path)

```
Homepage         Train List        Passenger        Seat Selection     Payment          Confirmation
┌─────────┐    ┌──────────┐    ┌────────────┐    ┌─────────────┐    ┌──────────┐    ┌─────────────┐
│ Origin   │    │ Select   │    │ NIK        │    │ Choose      │    │ Method   │    │ Booking     │
│ Dest     │───▶│ Train +  │───▶│ Name       │───▶│ Gerbong +   │───▶│ Pay      │───▶│ Code        │
│ Date     │    │ Class    │    │ Phone      │    │ Seat Number │    │ Confirm  │    │ E-Ticket    │
│ Pax      │    │ Price    │    │ Email      │    │             │    │          │    │ PDF         │
└─────────┘    └──────────┘    └────────────┘    └─────────────┘    └──────────┘    └─────────────┘
```

**Each transition is a potential failure point:**
- Homepage → Train List: search returns empty, station not found, date in past
- Train List → Passenger: train sold out between view and click, session expired
- Passenger → Seat: validation fails (NIK format, phone format)
- Seat → Payment: seat taken by another user during selection
- Payment → Confirmation: payment timeout, gateway error, insufficient balance

## Automation Scope

### In Scope (Automate)

| Feature | ROI | Reason |
|---------|-----|--------|
| Train Search | Very High | Entry point, stable form, fast feedback |
| Login | Very High | Gates all flows, simple to validate |
| Passenger Form | High | Rich validation (NIK, phone, email) |
| Seat Selection | High | Interactive but predictable (grid click) |
| Payment Page (UI only) | High | Verify method selection — NEVER process real payment |
| E2E Happy Path (mocked) | Very High | Combines all features, catches integration bugs |
| Negative validation | High | NIK format, empty fields, past dates |

### Out of Scope

| Feature | Reason | Alternative |
|---------|--------|-------------|
| Real payment processing | Charges real money | Mock at API/gateway level |
| OTP verification | SMS-based, non-automatable | Skip or mock if API allows |
| CAPTCHA | Anti-bot | Test flows that don't trigger it |
| External payment redirect | Bank/e-wallet page (not our code) | Test up to redirect URL |
| Real seat availability | Live inventory changes constantly | Use popular route D+7, accept variability |
| Email/SMS delivery | External channel | Verify trigger, not delivery |

### Mock Strategy

| Scenario | How to Mock |
|----------|-------------|
| Payment success | `page.route("**/payment/**", ...)` → return success JSON |
| Payment declined | Mock → return decline status code |
| Train sold out | Mock search API → return 0 seats |
| Session timeout | Delete session cookie mid-flow |
| Network error | `page.context.set_offline(True)` |

## Key Risks & Mitigations

| Risk | Impact | Mitigation |
|------|--------|-----------|
| Real payment triggered | Financial loss | NEVER click final pay — mock or stop before |
| OTP blocks login | Can't complete auth flow | Use pre-authenticated session cookie |
| CAPTCHA on login | Blocks automation | Test at off-peak hours, use session tokens |
| Seat sold between select and confirm | Test flakes | Use D+7 date, unpopular time slot |
| Site blocks automation (rate limit) | Tests fail | Add delays between requests, rotate sessions |
| Bahasa Indonesia UI | Assertion strings | All expected texts in Indonesian |
| jQuery page reloads | Slow tests | Wait for full page load between steps |

## Special Notes (Senior QE Perspective)

1. **This is NOT a SPA** — expect full page reloads between steps. Use `wait_for_load_state("load")` not `"networkidle"`
2. **Flexdatalist inputs** — station selectors use autocomplete. Must type + wait for dropdown + click suggestion
3. **Datepicker** — jQuery UI datepicker. Navigate months with next/prev buttons, then click day cell
4. **Session management** — site likely has 15-20 min timeout. Long test suites may need re-login between tests
5. **Real inventory** — tests must tolerate "no seats available" gracefully (retry with different date)
6. **Payment is destructive** — absolute rule: NEVER submit real payment in automation
